# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this is

A single-file SwiftUI macOS app (`main.swift`) that graphs live CPU temperature and mirrors it in a menu bar widget. No Xcode project — built directly with `swiftc`. See `README.md` for user-facing build/run instructions; this file is about how the code is put together and how to iterate on it.

## Build and run loop

```
swiftc -O main.swift -o TempMonitor
cp TempMonitor TempMonitor.app/Contents/MacOS/TempMonitor
cp Info.plist TempMonitor.app/Contents/Info.plist   # only needed if Info.plist changed
cp AppIcon.icns TempMonitor.app/Contents/Resources/AppIcon.icns   # only needed if the icon changed
pkill -f "TempMonitor.app/Contents/MacOS/TempMonitor"   # if already running
open TempMonitor.app
```

`swiftc -O main.swift -o TempMonitor` alone is enough to catch compile errors while iterating — only rebuild the `.app` bundle and relaunch when you want to see it run.

There is no test suite. Verifying behavior means actually launching the app and checking `ps aux | grep TempMonitor` for a live, non-crashing process, since automated screenshotting (`screencapture`, `osascript` UI scripting) hangs waiting on a screen-recording/accessibility permission dialog that can't be clicked through headlessly — don't burn time retrying that; report what you can verify and let the user eyeball the rest.

## Architecture

Everything lives in `main.swift`, organized by `// MARK:` sections:

- **`ThermalSpec`** — the single source of truth for temperature thresholds (`tjMax`, derived `yellow`/`red`, chart floor/ceiling). This app targets an iMac20,2 (i7-10700K, Tjmax 100°C per Intel ARK). If this ever runs on different hardware, this is the only place that needs to change.
- **`TemperatureReader`** — an `ObservableObject` singleton (`TemperatureReader.shared`). Owns the 1s polling `Timer`, threshold-crossing alert state, and an `onSample` closure hook the menu bar widget uses to redraw its icon. `rawHistory` (sized via `HistorySpec.rawCapacitySeconds`) is the only in-memory history buffer left — the last 5 minutes at full 1s resolution, backing the Live pane. Samples evicted from it feed a running accumulator that finalizes into one 5-minute average every `HistorySpec.bucketSeconds` evicted samples; that average is written straight through to `HistoryStore` (durable copy + retention pruning) and `rangeHistory` is refreshed from it — there's no in-memory bucket array anymore, `HistoryStore` is the sole source of truth for anything beyond the Live pane. `rangeHistory` is also refreshed on launch (`start()`) and whenever the UI picks a different `RangeSpec.Range` (`setRange(_:)`), so the Range pane survives a restart instead of coming up empty. `TemperatureReader` is a singleton and started exactly once, from `AppDelegate.applicationDidFinishLaunching`, specifically so polling and alerting keep running even when the SwiftUI window is closed/hidden — don't move `.start()` back into a view's `onAppear`, that ties the timer to view lifecycle and breaks the "window closed but menu bar still works" behavior.
- **`HistoryStore`** — a singleton (`HistoryStore.shared`) wrapping one SQLite connection at `~/Library/Application Support/TempMonitor/history.sqlite` (`import SQLite3`, macOS's built-in library — see the build note below). Schema is a single `bucket_samples(timestamp INTEGER PRIMARY KEY, temperature REAL NOT NULL)` table; `INTEGER PRIMARY KEY` makes `timestamp` the rowid, so retention pruning and the rollup query behind the Range pane are both plain range scans with no separate index. Opened with `PRAGMA journal_mode=WAL` for crash-safe atomic writes — the reason SQLite was chosen over a flat file. Retention (`RangeSpec.retentionSeconds`, 1 year) is enforced by deleting old rows every time a new bucket is inserted, not on a separate schedule.
- **`RangeSpec`** — defines the six selectable ranges (`Range.hour1` through `Range.year1`) as a window length plus a rollup granularity, queried live from `HistoryStore.rollup(granularitySeconds:windowSeconds:now:)` rather than kept as an in-memory array. `rollup` returns a fixed-length, time-aligned array of `windowSeconds / granularitySeconds` slots (oldest first, last slot = now), with `Double.nan` for slots that have no data — so `rangeHistory` always spans its full window and a sparse range (e.g. 1 Year with a few days of data) is mostly blank rather than stretched across the chart. The three shortest ranges (1 Hour/12 Hours/24 Hours) use `HistorySpec.bucketSeconds` itself as the granularity — since that already matches the native row spacing, each row lands in its own slot; 1 Week/30 Days roll up to hourly, 1 Year to daily. At 1-year retention the query touches at most ~105k rows, which SQLite handles in low single-digit milliseconds, comfortably within the once-per-5-minutes cadence it runs at.
- **`AppDelegate`** — bridges to AppKit for things SwiftUI's `WindowGroup` doesn't expose: the `NSStatusItem` (a hand-drawn thermometer icon — tube + bulb, `NSBezierPath` inside `lockFocus`/`unlockFocus` — filled to the 5-minute rolling average of `rawHistory`, not the raw per-second value, specifically so the menu bar doesn't visibly jitter every second; the hover tooltip shows the raw instantaneous value instead), intercepting the window's close button via `NSWindowDelegate.windowShouldClose` to hide (`orderOut`) instead of destroy the window, and `applicationShouldTerminateAfterLastWindowClosed` returning `false` so the app (and its menu bar icon) survives the window closing. The icon picks its ink color (outline/text) from `effectiveAppearance` at render time rather than using a template image, because it needs the mercury fill to keep its severity color in both light and dark menu bars. Exposed as `AppDelegate.shared` (set in `init()`) because SwiftUI's `@NSApplicationDelegateAdaptor` owns the instance and there's no other clean way to reach it from a `View`.
- **`WindowAccessor`** — a one-off `NSViewRepresentable` used purely to get a handle on the `NSWindow` hosting `ContentView`, so it can be handed to `AppDelegate.attach(window:)`. `NSApp.windows.first` was considered and rejected as fragile if more windows are ever added.
- **`TemperatureChart`** — a reusable single-array line chart (equal index spacing, threshold lines, grid) taking `values: [Double]` plus an optional `emptyMessage`. `NaN` values mean "no data": the line skips them, so it draws straight interpolated segments across interior gaps (smooth look, e.g. missed 5-minute buckets in the 24 Hours view) but leaves leading/trailing gaps blank — don't extrapolate past the first/last real sample, that's what keeps the 1 Year view mostly empty. Real samples also get small dots so isolated points show. The plot area is inset by `TemperatureChart.leftInset` (30pt) so the line never overlaps the y-axis labels; `TimeAxisLabels` uses the same inset. The Live pane left-pads `rawHistory` with `NaN` to `rawCapacitySeconds` (in `ContentView.livePadded`) so it always spans 5 minutes, and both `TimeAxisLabels` get the pane's full window length (not the data count), with labels switching to days for spans over two days. `ContentView` renders it twice as independent panes: `reader.rawHistory` (Live) and `reader.rangeHistory` (Range — toggled via a `.menu`-style `Picker` bound to `reader.selectedRange`/`setRange(_:)` across all six `RangeSpec.Range` cases), each with its own `TimeAxisLabels(totalSeconds:)` scaled to that pane's own span. `TemperatureChart` and `TimeAxisLabels` are generic over `[Double]`/`totalSeconds`, so the Range pane's window switching needs no per-range chart code. Both panes read `ThermalSpec` for scaling and threshold lines so they and the menu bar icon never disagree about what "yellow" or "red" means. `ContentView` also computes `rangeAverage` (mean of the non-NaN `rangeHistory` values) and colors it the same way, shown next to the Range pane's label.

## Conventions and constraints to preserve

- Keep this a single file unless it grows enough to justify splitting — it's intentionally a small, self-contained utility, not a full Xcode project. `HistoryStore`'s SQLite/C-interop code stays in `main.swift` for this reason, as a clearly delimited `// MARK:` section.
- `HistoryStore` calls (`insertBucket`/`pruneOlderThan`/`rollup`) are intentionally synchronous on the main thread, inside the same `DispatchQueue.main.async` block `readOnce()` already uses. They only run once per 5-minute bucket finalize (or once on launch/range change), and SQLite handles the worst case (~105k rows at 1-year retention) in low single-digit milliseconds — don't move this to a background queue, it adds thread-safety/`@Published`-hop complexity for no measurable benefit at this cadence and row count.
- `import SQLite3` autolinks against `/usr/lib/libsqlite3.dylib` via the SDK's module map under plain `swiftc` — verified with `otool -L` on the built binary. Don't add `-lsqlite3` or other linker flags defensively; they're not needed.
- Alerts (`checkThresholds`/`fireAlert` in `TemperatureReader`) are edge-triggered with hysteresis (`resetMargin`): a breach fires once, and won't fire again until the reading drops a couple degrees back below yellow. Don't change this to fire on every sample above a threshold — that was an explicit fix, not an oversight.
- Alerts intentionally layer three independent channels (`UNUserNotificationCenter` banner, `NSSound` chime, in-app banner) because the system notification permission is easy to deny or miss on first launch for an ad-hoc, unsigned `.app`; don't remove the sound/in-app fallbacks on the assumption the OS banner alone is enough.
- The app depends on the external `osx-cpu-temp` CLI (installed via Homebrew, path hardcoded as `/usr/local/bin/osx-cpu-temp`) rather than reading SMC keys directly in-process. That trade was deliberate: `osx-cpu-temp` already encodes the correct SMC sensor key selection across Mac models, and reimplementing that in Swift risks silently reading the wrong sensor.
- No dependency manager, no Package.swift — plain `swiftc`. Don't introduce SwiftPM/Xcode project scaffolding unless asked; it's not needed for a single-file app.
- `AppIcon.icns` is generated, not hand-edited: `make_icon.swift` draws `AppIcon.png` (same tube/bulb approach as `AppDelegate.updateIcon`, just larger and fixed at a 67°C reading) via `swift make_icon.swift`, then `sips`/`iconutil` build the `.icns` — see README's "Regenerating the icon". `AppIcon.png` and `AppIcon.iconset/` are intermediate/gitignored; only `make_icon.swift` (source) and `AppIcon.icns` (compiled result) are tracked. Don't hand-author or edit the `.icns` directly — change `make_icon.swift` and regenerate.
- The app is installed at `/Applications/TempMonitor.app` (`cp -R TempMonitor.app /Applications/TempMonitor.app`, then `touch` it and `killall Finder Dock` to bust macOS's icon cache if the icon changed) — that's a manual step for the user's own convenience, not part of the normal build/iterate loop above; don't re-run it automatically on every code change.
